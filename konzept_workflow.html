Three-Way-Matching: GoB-konformer Standard
Was ist Three-Way-Matching? In der professionellen Kreditorenbuchhaltung (Accounts Payable) werden drei Dokumente abgeglichen: (1) Bestellung/Rechnung → (2) Bankbuchung (Kontoauszug) → (3) Zahlungsbuchung im System. Stimmen alle drei überein, ist die Verbindlichkeit GoB-konform getilgt. In der WEG-Verwaltung entspricht dies: Rechnung (rechnungen) ↔ Kontoauszug (kontoauszug) ↔ Buchung (zahlungen mit rechnung_id).
🧾
Dokument 1: Rechnung

Verbindlichkeit: Wer hat wie viel berechnet?

rechnungen (rechnungsnummer, betrag_brutto, fällig)

🏦
Dokument 2: Kontoauszug

Zahlungsnachweis: Wann hat die Bank tatsächlich abgebucht?

kontoauszug (datum, betrag, buchungstext, iban)

💰
Dokument 3: Buchung

Buchhaltungsbeleg: Buchung im System mit Rechnung verknüpft

zahlungen (rechnung_id → rechnungen.id)

Matching-Algorithmus: Konzept & Pseudocode
Grundprinzip: Weighted Fuzzy Matching mit Confidence Score Jede offene Rechnung wird gegen jede nicht-zugeordnete Kontoauszugsbuchung bewertet. Der Confidence Score (0–100) ergibt sich aus drei gewichteten Teilscores. Liegt der Score ≥ 80, wird automatisch gebucht. Bei 60–79 wird ein Vorschlag angezeigt, der Benutzer bestätigt. Unter 60 bleibt die Buchung als "Offen" stehen.
# ── WEG-Hausverwaltung: Auto-Matching-Konzept ───────────────────────────── # Referenzen: SWIFT CGI-MP Best Practices v1.1 · Rillion 3-Way-Matching Guide def score_kontoauszug_gegen_rechnung(kb: dict, rechnung: dict) -> float: """ kb = kontoauszug-Zeile (datum, betrag, buchungstext, iban) rechnung = rechnungen-Zeile (rechnungsnummer, rechnungssteller, betrag_brutto, faelligkeitsdatum, rechnungsdatum) Rückgabe: Confidence Score 0.0 – 100.0 """ score = 0.0 # ── 1. BETRAG-MATCH (Gewicht: 40 Punkte) ───────────────────────────────── kb_betrag = abs(kb["betrag"]) # immer positiv vergleichen rg_betrag = rechnung["betrag_brutto"] differenz = abs(kb_betrag - rg_betrag) toleranz = rg_betrag * 0.01 # ±1 % (Skonto, Bankgebühren) if differenz == 0: score += 40 # exakter Treffer elif differenz <= toleranz: score += 35 # innerhalb Toleranz elif differenz <= rg_betrag * 0.05: score += 20 # < 5 % Abweichung (Teilzahlung?) # > 5 % → kein Betrag-Score # ── 2. DATUM-MATCH (Gewicht: 30 Punkte) ───────────────────────────────── # Buchungsdatum vs. Fälligkeitsdatum (±5 Werktage) tage = abs((kb["datum"] - rechnung["faelligkeitsdatum"]).days) if tage == 0: score += 30 elif tage <= 3: score += 25 elif tage <= 7: score += 15 elif tage <= 30: score += 5 # > 30 Tage → kein Datum-Score # ── 3. TEXT-MATCH (Gewicht: 30 Punkte) ────────────────────────────────── # Rechnungsnummer oder Rechnungssteller im Verwendungszweck? vzweck = kb["buchungstext"].upper() rgnr = (rechnung["rechnungsnummer"] or "").upper() steller = (rechnung["rechnungssteller"] or "").upper() if rgnr and rgnr in vzweck: score += 30 # Rechnungsnummer exakt gefunden elif fuzzy_ratio(rgnr, vzweck) > 85: score += 20 # Rechnungsnummer fuzzy elif steller and any(w in vzweck for w in steller.split() if len(w) > 3): score += 15 # Rechnungssteller erkannt return score # 0–100 def auto_match_alle(conn) -> list[dict]: """Führt Matching für alle nicht-zugeordneten Kontoauszugsbuchungen durch.""" ergebnisse = [] kb_offen = conn.execute( "SELECT * FROM kontoauszug WHERE zugeordnet=0 AND betrag<0 ORDER BY datum" ).fetchall() # nur Ausgaben (betrag negativ) rechnungen_offen = conn.execute( "SELECT * FROM rechnungen WHERE status IN ('Offen','Teilbezahlt')" ).fetchall() for kb in kb_offen: kandidaten = [] for r in rechnungen_offen: s = score_kontoauszug_gegen_rechnung(kb, r) if s >= 60: kandidaten.append({"rechnung": r, "score": s}) kandidaten.sort(key=lambda x: x["score"], reverse=True) if kandidaten: bester = kandidaten[0] if bester["score"] >= 80: # Auto-Buchung: direkt zuordnen + in zahlungen eintragen _auto_buchen(conn, kb, bester["rechnung"], bester["score"]) else: # Vorschlag für Benutzer speichern ergebnisse.append({"kb": kb, "vorschlaege": kandidaten[:3]}) return ergebnisse # wird in MatchingReviewDialog angezeigt
Score-Tabelle: Wann wird was ausgelöst?
ScoreAktionBegründungAnalogie Industry
≥ 80 ✅ Auto-Buchung (ohne Benutzerinteraktion) Betrag + Datum + Rechnungsnummer stimmen überein SAP S/4HANA: "Perfect Match" → automatische Verbuchung
60–79 💡 Vorschlag (Benutzer bestätigt) Betrag stimmt, Text/Datum weicht leicht ab Rillion/Tipalti: "Suggested Match" → 1-Klick-Bestätigung
30–59 ⚠️ Schwacher Treffer (manuelle Prüfung) Nur Betrag oder nur Text stimmt HighRadius: "Exception Queue" → AP-Clerk prüft
< 30 ❌ Kein Treffer (bleibt offen) Keine sinnvolle Übereinstimmung Neuer Vorgang: Rechnung noch nicht erfasst
Neue DB-Tabelle: kontoauszug_match_log
-- Matching-Protokoll: GoB-konformer Audit Trail CREATE TABLE IF NOT EXISTS kontoauszug_match_log ( id INTEGER PRIMARY KEY AUTOINCREMENT, kontoauszug_id INTEGER NOT NULL REFERENCES kontoauszug(id), rechnung_id INTEGER REFERENCES rechnungen(id), zahlung_id INTEGER REFERENCES zahlungen(id), score REAL, -- Confidence Score 0–100 methode TEXT, -- 'auto'|'manuell'|'vorschlag' benutzer TEXT, erstellt_am TEXT DEFAULT (datetime('now')), bestaetigt_am TEXT, abgelehnt INTEGER DEFAULT 0 );

Diese Tabelle macht jeden Matching-Schritt nachvollziehbar — Pflicht für GoB-konforme Buchführung (§ 239 HGB: Unveränderbarkeit und Nachvollziehbarkeit).

Lerneffekte & Feedback Loop
🧠
Aus manuellen Zuordnungen lernen

Wenn der Benutzer eine Buchung manuell einer Rechnung zuordnet, wird das Match-Muster gespeichert. Zukünftige Buchungen vom selben Rechnungssteller mit ähnlichem Betrag erhalten automatisch einen höheren Text-Score.

  • Rechnungssteller → bekannte Verwendungszweck-Muster
  • Kategorie-Vorschläge verbessern sich (vorschlag_kategorie)
  • Confidence-Schwellwert anpassbar (Einstellungen)
📈
Match-Rate messen (KPI)

Im Dashboard sollte die Auto-Match-Rate sichtbar sein:

  • Auto-Match-Rate: % Buchungen ≥ 80 Score
  • Offene Positionen: Kontoauszug ohne Rechnung
  • Unverbucht: Rechnungen ohne Kontoauszug-Match
  • Durchlaufzeit: Ø Tage Rechnungseingang → Bezahlt
